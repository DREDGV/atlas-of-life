# Разработка Atlas

Источник правил — корневой `AGENTS.md`, текущего этапа — `docs/ROADMAP_REVIVAL.md`.
Используй уже прочитанный актуальный контекст; при смене checkout проверь его заново.

## От запроса к результату

1. Проверь `git status --short`, `git status -sb`, `git log -1 --oneline` и относящийся к задаче PR. Отдели исходные локальные изменения от своей работы.
2. Сформулируй пользовательский сценарий, критерий готовности и границы. Для обычной реализации держи план коротким; отдельный план-документ полезен для сложной работы или передачи, но не является обязательным предварительным ответом.
3. Проследи фактическую цепочку UI → Core → storage → Sync → повторное открытие. Проверь, какие addons действительно подключены, если они затрагивают сценарий. Исторические handoff не заменяют код.
4. Выполни весь согласованный сценарий. Устраняй непосредственно связанные препятствия; новую roadmap-функцию не добавляй без запроса.

## Проверка по риску

- Data/Sync: focused regression на затронутый инвариант, успешное сохранение и отказ; сохранённое состояние проверять после reload. Sync — минимум два независимых клиента, если меняется межустройственный сценарий.
- UI: живой browser smoke с тестовыми данными и осмотром screenshot. Для обработки записи пройти создание → назначение → сохранение → открытие результата → возврат, когда он предусмотрен. CSS не проверять искусственными строковыми assertions.
- Документация/skills: проверить ссылки, структуру и согласованность; runtime suite без изменения runtime не требуется.
- Перед завершением продуктового куска запусти `powershell -NoProfile -ExecutionPolicy Bypass -File tools/verify-baseline.ps1`. Повторять весь baseline только после новых относящихся к нему изменений/ошибок. Focused JS-тесты запускай как `node tests/<name>.mjs`, а не буквальным wildcard в PowerShell.
- После прохождения достаточных проверок завершай задачу; не переходи в общий аудит.

## Завершение

Для законченных изменений следуй Git/PR правилам `AGENTS.md`: stage только названных файлов → commit → push → проверить удалённый HEAD/CI. Без merge по собственной инициативе. Не включай личные настройки Codex, backup и QA-артефакты в продуктовый commit.

В отчёте: что пользователь может сделать, изменённые области, доказательства проверок, ограничения, branch/HEAD/PR/CI. Различай «код готов», «проверено в браузере», «проверено на физическом телефоне» и «развёрнуто».
