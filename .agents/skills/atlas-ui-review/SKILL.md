# UI/UX Atlas

Сначала определи, что человек пытается сделать и какое наблюдаемое затруднение мешает. Сверь текущий интерфейс и реально подключённые модули; при доступном браузере сначала посмотри исходное состояние.

## Выбор изменения

- Отличай поломку, трудность действия, неверную визуальную иерархию, accessibility и вкусовое пожелание. Первые четыре приоритетнее необязательного redesign.
- Сохраняй существующий визуальный язык Atlas. Для локальной правки используй текущие tokens, типографику и компоненты; новый стиль не нужен.
- Если пользователь поручил полноценный lifecycle, исправляй необходимые Core/UI связи в его пределах. Не прекращай согласованную работу только потому, что она затрагивает несколько слоёв. Расширение за пределы запроса обозначай отдельно.

## Наблюдаемая готовность

- Главное действие понятно; после него видно, что получилось, где находится результат и как его открыть.
- Active, compact, final и empty states не смешиваются. В Processing одна активная карточка; завершённые записи не выглядят незаполненными формами.
- Основное, вторичное и опасное действия различаются. Ошибка сохранения видна и не уничтожает введённый текст.
- Клавиатура: focus, Enter/Escape, labels, отсутствие случайных hotkeys внутри редакторов.
- Текст/даты читаемы; цвет не единственный носитель смысла; длинный и многострочный пользовательский текст не ломает layout.
- Проверяй целевую ширину экрана и переход Inspector ↔ контекст/карта. Мобильный Capture проверяй отдельно, когда он затронут.
- Для persisted flow проверяй reload и возврат/отмену; успешный DOM-клик без проверки результата недостаточен.

Используй отдельный browser profile и тестовые данные; реальные данные пользователя не сбрасывай. Screenshot сохрани в `output/playwright/` и действительно просмотри. Одного осмысленного smoke и нужных regression checks достаточно; не вводи CSS assertions ради покрытия.
