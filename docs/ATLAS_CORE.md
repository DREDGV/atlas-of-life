# Atlas Core — команды и журнал операций

Обновлено: 3 августа 2026 года.

## Зачем нужен этот слой

Android и ПК не должны изменять данные разными способами. Команда описывает осмысленное действие пользователя, применяет его к локальному состоянию и добавляет запись в журнал. Сохранение состояния и операции происходит вместе.

```text
Интерфейс → команда → изменение state → запись operationLog → saveState
```

Журнал нужен для:

- будущей синхронизации Android ↔ ПК;
- восстановления после ошибок;
- общего Undo;
- разбора конфликтов;
- понятной истории изменений без привязки к конкретному интерфейсу.

## Текущая реализация

- `js/core/device.js` выдаёт стабильный локальный `deviceId`. Он хранится отдельно от пользовательского экспорта, чтобы импорт на новое устройство не клонировал идентичность старого устройства.
- `js/core/operations.js` создаёт неизменяемые снимки операций и ограничивает журнал последними 1000 записями.
- `js/core/commands.js` содержит первые команды и сохраняет состояние после успешного изменения.
- Схема состояния обновлена до версии 4.

Сейчас через команды проходят:

- `task.create` — быстрый ввод и создание задачи из инспектора;
- `task.update` — изменение названия, тегов, статуса и основных полей задачи;
- `task.move` — перенос задачи между проектами и доменами или изменение позиции независимой задачи;
- `task.move.undo` — точное восстановление проекта, домена и позиции предыдущего переноса;
- `task.delete` — удаление задачи со снимком удалённой записи;
- `task.promote_to_project` — атомарное превращение задачи в проект;
- `project.create` — создание проекта из инспектора домена;
- `inbox.capture` — захват каждой входящей записи;
- `inbox.delete` — удаление записи;
- `inbox.restore` — Undo удаления;
- `inbox.convert_to_task` — атомарное преобразование входящей записи в задачу.

Инспектор, экран «Сегодня» и все подтверждаемые переносы задач на карте больше не меняют задачи напрямую. Drag-and-drop использует ту же команду, что будущий мобильный и синхронизационный интерфейс. Обновление, в котором фактически ничего не изменилось, не создаёт лишнюю операцию. Служебное поле интерфейса `_type` удаляется на границе загрузки, сохранения и экспорта и не смешивается с пользовательскими сущностями.

## Формат операции

```json
{
  "schema": 1,
  "id": "op-...",
  "deviceId": "...",
  "timestamp": 1785700000000,
  "type": "inbox.capture",
  "entityType": "inbox",
  "entityId": "inbox-...",
  "baseVersion": null,
  "payload": {},
  "syncStatus": "pending"
}
```

`payload` является снимком на момент команды: последующие изменения объекта не переписывают старую операцию.

## Ограничения текущего этапа

- Журнал локальный и пока никуда не отправляется.
- Не все старые действия приложения переведены на команды.
- Операции ещё не воспроизводятся автоматически на пустом состоянии.
- Нет подтверждения доставки, разрешения конфликтов и шифрования синхронизации.
- Журнал входит в пользовательский экспорт, но не должен попадать в диагностические отчёты с личным текстом без явного согласия.

## Следующий порядок перевода

1. Автоматический локальный снимок перед импортом, миграцией и каскадным удалением домена.
2. Переименование и основные изменения проектов.
3. Создание, переименование и архивирование доменов.
4. Перенос проектов между доменами.
5. Универсальный Undo для обновления, удаления и остальных опасных действий.
6. Воспроизведение журнала на пустом состоянии.

После этого можно проектировать воспроизведение операций и первый локальный протокол обмена между двумя устройствами.
