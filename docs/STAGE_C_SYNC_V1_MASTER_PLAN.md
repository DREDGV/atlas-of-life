## 1. Назначение документа

Stage C превращает уже работающие локальные части Atlas of Life в одну межустройственную систему.

К этому этапу у проекта уже есть:

- надёжный Capture;
- Inbox;
- Processing Center;
- Atlas Core;
- безопасные Core commands;
- локальный operation log;
- Sync Foundation C0.

Цель Stage C — не «синхронизировать вообще всё», а довести до реальной ежедневной пользы первый сквозной межустройственный поток:

```text
Телефон
↓
Capture
↓
Inbox
↓
Remote Sync
↓
ПК
↓
Processing Center
↓
результат обработки
↓
Remote Sync
↓
Телефон
```

К концу Stage C пользователь должен иметь возможность спокойно жить между телефоном и ПК, не думая о том, где физически была создана запись.

# 3. Главный продуктовый результат Stage C

Stage C считается завершённым не тогда, когда появилось много Sync-модулей, а когда работает реальный пользовательский сценарий:

```text
1. Пользователь записывает мысль на телефоне.

2. Запись сохраняется локально сразу,
   даже если интернет отсутствует.

3. Когда сеть доступна, запись синхронизируется.

4. На ПК запись появляется в Processing Center.

5. Пользователь разбирает её:
   Task / Thought / Note / discarded.

6. Результат обработки синхронизируется обратно.

7. Телефон показывает актуальное состояние
   и понятный результат обработки.

8. Повторная доставка не создаёт дублей.

9. Ошибка сети не уничтожает данные.

10. Конфликт не решается тихим затиранием данных.

11. Пользователь понимает,
    работает Sync или требует внимания.

12. Подключение устройства не требует ручного
    экспорта/импорта JSON.
```

# 4. Что Stage C НЕ должен превратиться

Stage C — это **Sync v1**, а не «Full Distributed Atlas».

До завершения Stage C не следует самовольно затаскивать в него:

- полный Tasks CRUD sync;
- полный Projects sync;
- полный Domains sync;
- Map layout;
- Today state;
- отдельные Note/Thought entities;
- attachments;
- original audio;
- весь operation history;
- универсальный knowledge graph;
- AI state;
- полный CRDT;
- WebSocket/realtime только ради realtime;
- сложную account platform;
- enterprise multi-user permissions;
- Native Android background service;
- push notifications как отдельный продуктовый этап.

Если маленькая часть соседней сущности необходима именно для работающего Inbox/Processing flow, допустим минимальный bridge/projection. Но это не лицензия на превращение C2 в Full Sync.

# 5. Архитектурные инварианты Stage C

На всём протяжении Stage C сохраняются правила:

## 5.1 Local-first

```text
локальное действие
→ локально сохраняется
→ затем синхронизируется
```

Удалённый сервер не должен становиться обязательным для создания записи, редактирования Inbox или Processing.

## 5.2 Operations, not whole JSON

Sync передаёт операции/события изменения, а не заменяет общий state blob целиком.

Нельзя возвращаться к схеме:

```text
скачать JSON
→ перезаписать весь localStorage
```

как к основному механизму Sync.

## 5.3 Persisted state только через Core

Transport/UI/Sync adapter не должны напрямую изменять persisted state.

Входящая удалённая операция применяется через Core remote-apply semantics с сохранением атомарности и инвариантов.

## 5.4 `rawText` immutable

Исходный Capture должен сохраняться.

Редактирование текущего текста не должно уничтожать оригинальную пользовательскую запись.

## 5.5 Idempotency

Один `operationId` применяется максимум один раз.

Retry, reconnect и повторная доставка должны быть безопасными.

## 5.6 No silent data loss

Запрещены:

- silent last-write-wins там, где возможна потеря данных;
- молчаливое удаление unacked outbox operations;
- игнорирование storage failure как успеха;
- бесконечно зависшая операция без видимого состояния;
- продвижение cursor мимо ошибки без durable фиксации причины.

## 5.7 Sync не блокирует Atlas

Если remote service временно недоступен:

```text
Capture работает
Processing работает
локальные данные сохраняются
outbox ждёт
позже Sync догоняет
```

# 7. C0 — Sync Foundation

**Версия:** `0.11.0-alpha.1`  
**Статус:** ✅ завершён  
**Назначение:** доказать корректный фундамент Sync до подключения настоящего backend.

## 7.1 Что уже реализовано

C0 создал:

- устойчивый `deviceId`;
- монотонный per-device `sequence`;
- immutable sync operation envelope;
- отдельный durable outbox;
- delivery metadata;
- ack semantics;
- retry/recovery;
- idempotency/deduplication;
- cursor/pull model;
- persisted quarantine;
- conflict detect + refuse;
- remote apply через Core;
- dev/local relay transport;
- первый Inbox/Processing vertical slice.

## 7.2 Текущий operation envelope

Рабочая форма:

```js
{
  schema,
  id,          // canonical operationId
  deviceId,
  sequence,
  timestamp,
  type,
  entityType,
  entityId,
  baseVersion,
  payload
}
```

Локальные delivery metadata живут отдельно:

```js
{
  syncStatus,
  attempts,
  lastError
}
```

## 7.3 Что не надо заново строить в C1

Без обнаруженного реального blocker агент не должен снова перепроектировать:

- operation IDs;
- базовую idempotency;
- outbox с нуля;
- local relay как тестовый механизм;
- cursor semantics;
- quarantine только ради «более красивой архитектуры».

C0 — фундамент, а C1 должен вывести его в реальную сеть.

# 8. C1 — Real Remote Sync

**Целевая версия:** `0.11.0-alpha.2`  
**Статус:** 🔴 CURRENT

## 8.1 Продуктовая цель

Превратить C0 из локального прототипа Sync в реальную межустройственную функцию.

Definition of Done C1 в одной строке:

```text
независимое устройство A
↔ настоящий network transport
↔ независимое устройство B
```

с реальным Inbox/Processing lifecycle.

## 8.2 Что агент должен исследовать самостоятельно

Перед реализацией агент изучает:

- текущее устройство приложения;
- hosting/backend возможности проекта;
- PWA ограничения;
- существующий deployment;
- C0 transport contract;
- способы хранения операций на сервере;
- security boundary;
- pairing;
- network lifecycle;
- offline/retry;
- конфигурацию телефона и desktop.

Агенту разрешено самостоятельно выбрать технический путь.

Не нужно заранее считать Firebase, Supabase, Cloudflare, Node или другой provider обязательным.

Критерии важнее бренда.

## 8.3 Требования к remote backend

Remote service должен минимально поддерживать:

```text
push operations
pull operations after cursor
dedupe by operationId
server ordering / cursor
isolation of one user's sync space
ack semantics
safe retry
```

Backend не обязан быть «финальной платформой Atlas на десять лет».

Он должен быть:

- маленьким;
- понятным;
- достаточно безопасным;
- расширяемым;
- удобным для реальной эксплуатации;
- не требовать секретов в клиентском Git.

## 8.4 Security boundary

C1 должен исключить модель:

```text
знаешь URL → читаешь чужой Atlas
```

Нужна минимальная, но реальная изоляция.

Допустимые направления:

- sync-space ID + secret;
- pairing token;
- device registration;
- derived credentials;
- иной простой механизм.

Точные решения выбирает агент после изучения архитектуры.

Обязательные свойства:

- секреты не коммитятся;
- один sync-space не видит данные другого;
- credentials можно заменить/revoke;
- секрет не должен случайно попадать в URL/лог, если это создаёт утечку;
- local state остаётся доступным без remote credentials.

Полноценные username/password/accounts не являются обязательными.

## 8.5 Pairing / подключение второго устройства

Пользователь должен иметь реалистичный путь подключения телефона и ПК.

Рабочая концепция:

```text
устройство A создаёт / имеет Sync space
↓
пользователь безопасно переносит pairing data
↓
устройство B присоединяется
↓
оба получают доступ к одному operation stream
```

Это может быть:

- короткий pairing code;
- QR;
- вручную введённый secret;
- другой простой flow.

Выбор UI/механизма — зона инженерного решения агента.

Не строить огромный setup wizard.

## 8.6 Runtime lifecycle

C1 должен определить, когда реально запускается Sync.

Агент самостоятельно выбирает простую стратегию, например комбинацию:

- sync после локального syncable command;
- sync при старте;
- sync при возвращении вкладки;
- периодический polling;
- ручная кнопка Retry/Sync;
- событие `online`;
- Processing completion.

Не нужно realtime любой ценой.

Предпочтение:

```text
простая предсказуемая синхронизация
>
сложная магическая realtime-инфраструктура
```

## 8.7 Offline → Online

Обязательный сценарий:

```text
телефон offline
↓
Capture создаётся
↓
operation в durable outbox
↓
пользователь продолжает работу
↓
сеть появляется
↓
outbox отправляется
↓
ПК получает запись
```

Remote outage не должен блокировать Capture.

## 8.8 Минимальный Sync UX

К концу C1 Sync уже должен быть видимой функцией приложения.

Пользователю нужно понимать как минимум:

- включён ли Sync;
- есть ли pending operations;
- когда был последний успешный sync;
- произошла ли ошибка;
- можно ли повторить.

Возможные состояния:

```text
Синхронизировано
Синхронизация…
Ожидают отправки: N
Нет сети
Ошибка синхронизации
Требуется внимание
```

Не нужно строить отдельную гигантскую Sync Dashboard.

## 8.9 C1 должен доказать реальный network flow

Не достаточно:

- unit test;
- два объекта engine в одном процессе;
- два tab одного профиля с общим localStorage;
- mock server.

Нужна реальная возможность:

```text
browser/device A
→ сеть
→ remote service
→ browser/device B
```

Если среда агента не позволяет физический smoke, он должен подготовить всё до последнего внешнего шага и дать точную инструкцию проверки.

## 8.10 Допустимые изменения архитектуры

В C1 агент вправе:

- изменить transport interface;
- добавить remote transport adapter;
- реорганизовать `js/sync/*`;
- добавить server/backend directory;
- добавить небольшой Sync settings UI;
- добавить pairing module;
- добавить network lifecycle coordinator;
- добавить конфигурацию окружения;
- исправить C0 API, если реальный backend показал дефект;
- удалить/упростить мёртвый C0-код.

Но не выполнять общий рефакторинг Atlas без связи с C1.

## 8.11 Decision points, где агент должен остановиться

Агент не должен молча принимать решение, если требуется:

- платный сервис;
- новый внешний аккаунт пользователя;
- DNS/domain;
- секрет/API key от пользователя;
- долгосрочная vendor lock-in архитектура;
- изменение privacy model;
- существенное изменение roadmap;
- публичный production deployment за пределами доступной среды.

В этом случае агент обязан:

1. сделать всё возможное заранее;
2. описать blocker;
3. дать 2–3 варианта;
4. рекомендовать один;
5. попросить одно конкретное действие.

## 8.12 Definition of Done C1

C1 готов, когда:

- существует настоящий remote transport;
- два независимых клиента могут работать через него;
- Capture A приходит на B;
- Processing B создаёт обратную operation;
- A получает актуальный результат;
- offline Capture переживает отсутствие сети;
- retry не создаёт дублей;
- pairing/security boundary существует;
- Sync state виден пользователю;
- local relay честно остаётся dev/test transport;
- production transport не выдаётся за готовый, если deployment ещё не сделан.

# 9. C2 — Routed Result / Task Bridge

**Целевая версия:** `0.11.0-alpha.3`

**Реализованный подход (20.08.2026): Вариант B — read-only Task Result Projection.**

Подробности реализации — `docs/SYNC_C2_RESULT_BRIDGE.md`. Кратко: десктоп
эмитит `task.result.upsert` / `task.result.remove` рядом с routing и при
изменении/удалении/отмене routed-задачи; проекция (`title`, domain/project
titles, priority, structured due, status) хранится на других устройствах в
`state.taskProjections` (read-only, один писатель — десктоп) и рендерится в
Capture PWA карточкой результата; отсутствие проекции — честный fallback
«Результат недоступен на этом устройстве».

## 9.1 Почему C2 нужен

C0/C1 могут синхронизировать:

```text
Inbox item
→ processed
→ resultRef = task-123
```

Но если Task существует только на desktop, телефон знает ID результата, но не знает самого результата.

Для пользователя это неполноценное состояние.

Нужно превратить:

```text
"разобрано"
```

в:

```text
"создана задача:
Купить удобрение для сливы
Дача · Сад · Высокий · 24 августа"
```

## 9.2 Главная цель C2

Сделать результат Processing понятным и полезным на другом устройстве, не превращая C2 в Full Task Sync.

## 9.3 Что агент должен решить

После изучения кода выбрать лучший вариант:

### Вариант A — Result Snapshot

Inbox operation содержит достаточно immutable/derived данных результата:

```js
resultRef: {
  type: "task",
  id: "task-123",
  snapshot: {
    title,
    domainTitle,
    projectTitle,
    priority,
    due
  }
}
```

Плюсы:

- простота;
- нет полноценного Task replication.

Минусы:

- snapshot устаревает при изменении Task.

### Вариант B — Minimal Task Projection

На второе устройство синхронизируется ограниченное read-only представление Task:

```js
{
  id,
  title,
  domain,
  project,
  priority,
  due,
  status
}
```

Это не полноценный Task CRUD, а projection результата.

### Вариант C — Limited Task Sync

Если фактическая архитектура показывает, что projection создаёт больше проблем, можно ввести небольшой ограниченный Task sync.

Но он должен оставаться ограниченным задачами, рожденными из текущего Processing flow, а не превращаться в общий Task Sync.

## 9.4 Критерии выбора подхода

Выбранная модель должна:

- не ломать `resultRef ↔ sourceInboxId`;
- давать телефону понятный результат;
- не требовать полного Projects/Domains sync;
- безопасно переживать изменение результата;
- позволять будущему Full Sync эволюционировать без болезненной миграции;
- не создавать две конкурирующие истины о Task.

## 9.5 Изменение Task после Routing

C2 должен определить поведение минимум для ситуаций:

```text
Task создана
→ позже переименована

Task создана
→ изменён priority/due

Task создана
→ удалена

Task создана
→ route reverted
```

Телефон не должен бесконечно показывать явно ложный результат без какой-либо стратегии обновления.

## 9.6 UX на телефоне

Processed routed item должен показывать понятный результат.

Пример:

```text
✓ Разобрано

Задача
Купить удобрение для сливы

Дача · Сад
Высокий · 24 августа
```

При отсутствии результата:

```text
Результат недоступен на этом устройстве
```

лучше, чем битая ссылка или пустая карточка.

## 9.7 Definition of Done C2

C2 готов, когда:

- routed Inbox item на другом устройстве показывает содержательный результат;
- Task bridge не требует Full Atlas Sync;
- update/delete/revert результата имеют определённое поведение;
- нет broken `resultRef`;
- телефон не обязан иметь полный desktop task model ради отображения результата.

# 10. C3 — Multi-device Conflicts & Recovery

**Целевая версия:** `0.11.0-alpha.4`

**Реализованный подход (26.08.2026): классификация + человеческое разрешение без CRDT.**

Подробности — `docs/SYNC_C3_CONFLICTS.md`. Кратко: quarantine обогащён
`conflictStatus`/`resolution`; гонка «update для локально удалённой записи»
классифицируется как `deleted_race` (а не падает/quarantine-invalid);
пользователь разрешает в панели Sync: base_version → оставить/принять/
сохранить обе, deleted_race → оставить удалённой/восстановить и применить
(восстановление доставляется остальным); resolution durable. Дополнительно
в C3: синхронизация удаления/восстановления Inbox (W2) и обновление
проекций результата при rename Domain/Project (W3).

## 10.1 Цель

C0 уже умеет не затирать конфликт молча.

C3 должен сделать конфликты и recovery пригодными для реального человека.

Не строить универсальную математику распределённых данных для всего будущего Atlas.

Работать только с конфликтами, реально возникающими в Stage C.

## 10.2 Основные реальные конфликтные сценарии

### Сценарий 1

```text
Phone offline
↓
пользователь редактирует Inbox
↓
Desktop уже обработал старую версию
↓
Phone возвращается online
```

### Сценарий 2

```text
два устройства редактируют одну запись почти одновременно
```

### Сценарий 3

```text
одно устройство discard
другое process
```

### Сценарий 4

```text
route_to_task
vs
редактирование старой Inbox версии
```

### Сценарий 5

```text
remote operation ссылается на состояние,
которого на устройстве ещё нет
```

## 10.3 Conflict policy

Вместо silent LWW должны быть определены безопасные действия.

В зависимости от типа конфликта:

- принять remote;
- оставить local;
- создать копию;
- восстановить обе версии;
- отложить operation;
- повторить после получения dependency.

Агент выбирает минимально достаточную модель.

## 10.4 Пользовательский conflict UX

Пользователю не нужен термин «baseVersion mismatch».

Нужен человеческий смысл:

```text
Эта запись была изменена на другом устройстве.

Локальная версия:
...

Версия с другого устройства:
...

[Оставить локальную]
[Принять другую]
[Сохранить обе]
```

Не все три действия обязательны для каждого типа конфликта.

## 10.5 Quarantine

Persisted quarantine C0 остаётся техническим фундаментом.

C3 может добавить:

- conflict classification;
- resolution status;
- retry after resolution;
- связь conflict → entity;
- небольшой пользовательский entry point.

Не превращать quarantine в полноценную audit platform.

## 10.6 Recovery

C3 должен закрыть реальные проблемы:

- stale cursor;
- remote temporary failure;
- reconnect после долгого offline;
- failed outbox entry;
- partial sync;
- operation dependency missing;
- повторное подключение устройства;
- local state сохранился, remote state продвинулся далеко.

## 10.7 No CRDT by default

CRDT/OT/сложный merge engine допустимы только если агент докажет, что реальные Stage C сценарии не решаются проще.

Сложность должна оправдываться реальным пользовательским конфликтом.

## 10.8 Definition of Done C3

C3 готов, когда:

- основные Inbox/Processing конфликты не уничтожают данные;
- конфликт переживает reload;
- пользователь может понять и разрешить нужные конфликтные состояния;
- resolution не создаёт echo/duplicate loops;
- offline client может безопасно догнать remote;
- одна плохая operation не ломает весь stream.

# 11. C4 — Sync v1 Product Closure

**Целевая версия:** `0.11.0-alpha.5`

## 11.1 Цель

C4 — не новый фундамент.

Это превращение Sync v1 в законченную пользовательскую функцию.

К этому моменту уже должны работать:

- network transport;
- pairing;
- Inbox/Processing round-trip;
- Task/result bridge;
- основные conflict/recovery сценарии.

## 11.2 Initial bootstrap нового устройства

Новый клиент должен получить необходимое актуальное состояние без ручного JSON import.

Нужно определить:

- replay operations from zero;
- snapshot + tail;
- server bootstrap endpoint;
- другой механизм.

Агент выбирает подход по фактическому объёму operation stream.

Не нужно преждевременно строить сложный snapshot service, если полный replay пока практически достаточен.

## 11.3 Device management

Минимальная понятная модель:

```text
Мои устройства

Телефон Nokia
ПК
```

Полезные возможности:

- увидеть подключённые устройства;
- понятное имя устройства;
- последнее соединение;
- unlink/revoke;
- подключить новое.

Не нужен корпоративный MDM.

## 11.4 Disable / unlink Sync

Очень важный принцип:

```text
отключить Sync
≠
удалить локальный Atlas
```

Пользователь должен иметь возможность:

- выключить автоматический Sync;
- отвязать устройство;
- сменить sync-space;
- оставить локальные данные.

Разрушительные действия должны быть явно отделены.

## 11.5 Sync state UX

К концу C4 состояние Sync должно быть читаемо без developer console.

Например:

```text
✓ Синхронизировано

⟳ 3 изменения ожидают отправки

○ Нет сети — изменения сохраняются локально

! Ошибка синхронизации
  [Повторить]

⚠ 1 конфликт требует решения
```

Точная визуальная реализация — задача агента/UI review.

## 11.6 Diagnostics

Нужен минимальный диагностический слой, полезный при реальном сбое.

Можно показывать/экспортировать:

- deviceId;
- sync-space identifier без секрета;
- pending count;
- failed count;
- cursor;
- lastSyncAt;
- lastError;
- conflict count;
- backend reachability.

Не выводить секреты.

## 11.7 Реальная эксплуатация

C4 должен включать короткий реальный пользовательский прогон:

```text
Phone Capture
Desktop Processing
Phone result

offline Phone
online recovery

несколько последовательных записей

перезапуск браузера/PWA

ошибка сети

повторный sync
```

Это не повтор всех исторических тестов Stage A/B.

Нас интересует именно реальный межустройственный flow.

## 11.8 Definition of Done C4

Stage C закрывается, когда:

- Phone ↔ Desktop flow работает через настоящий remote service;
- подключение устройства понятно;
- новый клиент может bootstrap;
- offline не ломает Capture;
- retry работает;
- result Processing виден на обоих устройствах;
- основные конфликты разрешимы;
- unlink не уничтожает local Atlas;
- Sync status понятен;
- secrets не попадают в Git/UI logs;
- C4 прошёл реальную межустройственную эксплуатацию.

# 12. Definition of Done всей Stage C

Перед переходом в `0.12.x` должны выполняться все пункты:

## Core

- operations immutable;
- outbox durable;
- idempotency работает;
- remote apply через Core;
- cursor monotonic;
- quarantine persisted.

## Network

- настоящий remote transport;
- HTTPS;
- isolation sync spaces;
- retry;
- offline recovery.

## Product

- Capture с телефона появляется на ПК;
- Processing на ПК возвращается на телефон;
- routed result понятен;
- пользователь видит Sync status.

## Recovery

- duplicate delivery безопасна;
- network outage не уничтожает работу;
- основные multi-device conflicts не приводят к silent loss;
- reconnect работает.

## Devices

- pairing понятен;
- можно подключить второе устройство;
- можно unlink/revoke;
- initial bootstrap работает.

## Scope control

При этом НЕ требуется Full Sync всего Atlas.

# 20. Финальный принцип Stage C

Sync — не самостоятельная цель Atlas.

Он нужен, чтобы пользователь мог свободно переходить между устройствами, а Atlas при этом оставался одной системой.

Идеальный Sync в повседневной работе почти незаметен:

```text
мысль появилась
→ Atlas её сохранил
→ нужное устройство её увидело
→ пользователь продолжил жить
```

Всё остальное — инженерная механика под капотом.
