# Processing B0 — Follow-up: reversible Inbox → Task flow

**Дата:** 2026-08-18  
**Версия:** 0.10.0-alpha.1  
**Статус:** зафиксировано как follow-up; НЕ реализуется в Stage B0.

## Почему этот документ существует

Stage B0 намеренно не переделывает Inbox → Task conversion. Требование этапа:
сначала изучить текущий destructive conversion, зафиксировать его ограничения и
описать, каким должен быть безопасный обратимый Processing flow — отдельным
следующим шагом, без большого redesign внутри B0.

## Текущее поведение (по коду, ветка revival-preparation)

`js/features/inbox/model.js → convertInboxItemToTask(id, options)`:

1. Запись **удаляется из `state.inbox`** (через `removeInboxItem`).
2. Создаётся `Task` с `title = item.text`, без ссылки на исходную запись.
3. Команда `inbox.convert_to_task` пишет в operation log payload
   `{ source, sourceIndex, task }` — снимок источника сохраняется.

### Почему это деструктивно

| Проблема | Последствие |
|---|---|
| Запись физически удаляется | Нет обратного пути в Inbox; «исходник» живёт только в payload операции |
| Нет `undo` для конверсии | Ошибка пользователя (не та запись / не тот проект) необратима в UI |
| Нет ссылки `taskId` на записи | Нельзя увидеть «из какой мысли родилась задача»; повторный разбор невозможен |
| Нет `restore`-команды | Operation log не воспроизводим: replay на пустом состоянии не вернёт запись |
| Конверсия не учитывает `itemType`/`status` | Разбор и конверсия — два независимых мира |

## Требования к безопасному reversible flow (будущий этап)

1. **Исходная запись не уничтожается**:
   - запись остаётся в Inbox с `status: processed` (или `reviewed`), либо
   - удаляется только вместе с полным undo-токеном и командой `inbox.restore`-конверсии.
2. **Ссылка на результат**: запись получает `taskId` (или конверсия — `sourceInboxId`),
   чтобы маршрутизация «мысль → задача» была видимой и обратимой.
3. **Обратимость командой**: `inbox.convert_to_task` дополняется
   `inbox.convert_to_task.undo` (удаление задачи + восстановление записи)
   или конверсия становится неразрушающей по умолчанию.
4. **Replay-safe**: payload операции достаточен для воспроизведения на пустом
   состоянии (включая `sourceIndex`, `domainId`, `projectId`, provenance).
5. **Учёт Processing-полей**: конверсия использует подтверждённый `itemType`
   (например, `task` → реальная Task; `thought`/`note` — не «выполняемые» сущности)
   и переносит `status` в жизненный цикл Task.
6. **UI**: в карточке разбора — «Разобрать» вместо необратимого «В задачу»;
   разобранные записи сворачиваются, но остаются видимыми/восстановимыми.

## Что B0 уже закладывает

- `itemType` и `status` живут на записи и проходят через Core command
  (`inbox.update`) с атомарностью и operation log — маршрутизация следующих
  измерений (Domain / Project / Entity / Topic / Context / due / priority)
  добавится как новые поля той же команды, без новой универсальной модели.
- `rawText`-инвариант: исходный захват сохраняется всегда — фундамент любого
  обратимого преобразования.
- Операции `inbox.update` несут `before/after` — готовый материал для undo.

## Следующий шаг (предлагаемый scope)

`0.10.0-alpha.2` (или отдельный PR внутри B-линии):

- `inbox.convert_to_task` → обратимая конверсия с `taskId`-ссылкой и undo;
- перенос `itemType`/`status` в конверсию;
- replay-тесты конверсии на пустом состоянии.
